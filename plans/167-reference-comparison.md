# 167 — 유사 서비스·오픈소스·운영 관행 비교와 제안 (2026-10-19, 운영자 결정 대기)

운영자 요구(2026-10-18): "유사 서비스·GitHub·MCP 등 남이 만든 것을 레퍼런스로 장단점을 비교하고, 기능·디자인 제안과 함께 보안·DB·운영 전반에서 배울 점을 제안하라. 메모리 부족·작업 트리·운영 관리가 체계적이지 않은 것이 걱정이다. 체계적이고 심플한 서비스를 만들고 싶다."

- 조사: sonnet 에이전트 3명(경쟁 서비스 / GitHub·MCP / 운영 관행), 출처 URL 포함 보고 → 계획자가 우리 코드·운영 수치와 대조.
- **직접 써 보지 못한 곳**: 호갱노노·직방·네이버부동산은 자동화 접근이 차단돼 **앱스토어 설명 기준**이다(아래 표에 "설명 기준" 표시). 그 밖은 공개 웹 화면 기준.
- 우리 쪽 수치는 2026-10-18 실측(health·Vercel·Supabase·코드)이다. 추정은 "추정"으로 표시.

**우리 강점(유지)**: 공식 실거래 181만 건·매일 적재·서버 렌더 단지/지역 페이지(SEO)·무료·광고 없음·매수 추천 없음·개인정보 최소.
**우리 약점(실측)**: 첫 화면 과밀(2026-10-14 전면 검토), 알림 종류 1개(관심 단지 새 거래), 데이터 기준일/수집일 이중 표기 없음, 모바일 앱 없음(PWA 만), 서버 렌더 페이지와 앱 테마 불일치.

### 기능·디자인 제안(괜찮은 것만)
1. **기준일/수집일 이중 표기**(S): 단지 상세·지역 페이지 상단 "실거래 기준 2026.10.17 · 수집 2026.10.18 02:45". 데이터 상태 띠의 값(`window._syncData`)을 그대로 쓴다. 환각 위험 없음.
2. **알림 종류 분리**(M, plans/166 3-3 과 합침): 새 거래 / 목표가 도달 / 데이터 지연(2일 이상 적재 없음). 목표가는 DB 열 추가가 필요하므로 운영자 승인 뒤.
3. **데이터 출처 한 페이지**(S): 이미 CLAUDE.md 의 출처 표가 있다 — `/data-sources` 서버 렌더 페이지로 공개(법령·공공데이터 라이선스 표기 포함).
4. **첫 화면 서울 칩·폼 통합·지도 화면 관심 관리**: plans/166 3-4 그대로(Claude Design 시안 뒤).

## 4. "체계적·심플" 을 위한 운영 규칙 제안(비용 0)
사용자 걱정(메모리 부족·작업 트리·관리)을 사실로 바꾸면:
- **배포가 너무 잦다**: 하루 71회(세션 하나가 만든 수). 규칙 — 미리보기 푸시는 묶음당 1회, 운영 푸시는 하루 3회 이하, 문서 커밋은 다음 코드 배포에 묶는다. 거절되면 커밋 상태 API 로 확인하고 기다린다(해제 실측 6.5시간).
- **작업 트리**: 살아 있는 작업 트리는 1개(p144)만. 끝난 미리보기 브랜치(preview/privacy-136·advisor/base-163)는 원격에서 지운다(브랜치 푸시 = 배포 1회).
- **단일 파일 프런트(index.html 14,700줄)**: 메모리 압박의 실제 원인(한 번 읽는 데 약 50만 토큰). 당장 쪼개지 않는다(테스트 807건이 문자열로 고정) — 대신 **읽을 때 함수 단위로만 읽는 규칙**과, 다음 큰 개편(3-4 IA) 때 화면별 파일 분리를 시안과 함께 결정.
- **세션 체크리스트 한 장**(CLAUDE.md 에 이미 4단계가 있다 — 지키는 것이 문제): verify → 미리보기 1회 → 운영 1회 → health deploy id → Sentry 30분 → 노트.
- **주간 점검표**(월요일, 5분): DB 사용량·Redis 명령·Sentry 신규·크론 마지막 성공·배포 수·백업 파일 날짜. 전부 `/api/health` 와 대시보드에서 읽는다.
