# 186 서비스 전체 점검 (2026-10-31)

운영자 요청: 처음 들어와서부터 전부 눌러 보고 기능, 비효율, 찾기 힘든 기능, UX, UI, 보안, 말투, 기능 제안을 확인.

## 방법
- 운영 사이트(https://myhomelog.vercel.app, 배포 fb1e97e)를 내장 브라우저로 직접 사용했다. 데스크톱 1024px, 800px, 1280px와 휴대폰 375px에서 확인했다.
- 확인한 화면: 소개 화면 검색, 지도, 단지 상세 탭 7개(종합의견, 실거래가, 위험, 특약 초안, 가격 신호, 단지 정보, 임장노트), 도구 메뉴 8개(특약, 청약, 대출 계산, 복비 계산, 거래 체크리스트, 갈아타기 계산, 사용법, 규제 요약), 브리핑, 목록 맞춤 찾기, 보고서 입력, 데이터 도우미. 콘솔 오류는 0건이었다.
- 코드를 읽는 세 갈래(문구 말투, 보안, 기능 제안 조사)는 sonnet 에이전트에게 맡겼다. 지적은 원문, 운영 로그, 운영 응답으로 다시 대조한 것만 반영했다.
- 로그인, 결제, 계정 생성은 하지 않았다(권한 규칙).

## 고친 것 (커밋 대상, 검사 1012 통과)
1. 요청 제한이 사실상 꺼져 있었다. 운영 로그에서 Upstash가 월 한도 초과(Limit 500000, Usage 500001)라 general, data, chatdata 제한이 모두 "장애 시 통과"였다. 이제 Redis가 실패하면 인스턴스 메모리 제한으로 내려간다. 비용 경로는 예전처럼 503이다(`backend/middleware/rateLimit.js` RL-MEM-FALLBACK).
2. 목록 맞춤 찾기 카드가 창 폭 800~1024px에서 깨졌다. 단지 이름 칸이 0px(800)과 31px(1024)로 눌렸다. 카드 폭에 맞춰 두 줄, 세 줄로 다시 배치한다(LIST-CARD-FIT, 컨테이너 쿼리). 1280px 이상과 휴대폰 배치는 그대로다. 운영 화면에 같은 규칙을 넣어 800, 1024, 1280에서 확인했다.
3. 검색이나 지도로 연 단지 상세에 "분석 대기"가 늘 붙었다. 점수는 목록 맞춤 찾기에서만 계산되므로 끝나지 않는 대기처럼 보였다. 점수가 없으면 표시하지 않는다(NO-PENDING).
4. 필요 현금 범위 하한이 (매매가 − 대출)보다 낮았다. 실측은 6.18억에 하한 6.16억이었고, 0.4억 계산에서는 백엔드 하한이 −0.14억이었다. 오차를 부대비용에만 적용하도록 프런트와 백엔드를 같은 식으로 고쳤다(CASH-RANGE). 기록 검사 두 값을 갱신했다.
5. 도우미 답에 조사 오류가 있었다("잠실엘스"을 → 를). 을/를을 받침으로 고르고, 답 문장의 긴 줄표 6곳을 쌍점으로 바꿨다.
6. 화면 제목과 공유 제목의 긴 줄표를 바꿨다(index.html 제목, og, twitter, 동적 제목 3곳, share.js 3곳, dataSources.js). 관련 검사 정규식은 `\|`로 이스케이프했다.
7. 결제 화면 상태 문구 17곳을 해요체로 바꿨다. "세션", "paymentKey/orderId/amount 누락", "결제 완료!"를 없앴다. 약관과 동의 문구는 법적 고지라 그대로 뒀다. 특약 점검 안내의 문체 섞임도 고쳤다.

## 기능 제안 (공개 자료 근거, sonnet 조사. 출처 URL은 조사 원문에 있음)
1. 단지 관리비와 장기수선충당금: 공공데이터포털 K-apt 관리비 API(무료). 단지 코드 연결은 이미 있다. 작업량 중간.
2. 데이터 시차 안내: 신고에서 공개까지 걸리는 시간을 화면에 밝힌다(국토부 안내 근거). 작업량 작음.
3. 조회 실패 시 다시 시도 버튼: 경쟁 앱 리뷰 요청. 작업량 작음.
4. 내 집과 관심 단지의 새 실거래 알림: 시세 추정 없이 사실만 알린다. 기존 푸시를 쓴다. 작업량 중간.
5. 제외: 가격 예측, 경매 입찰가, 투자 순위는 원칙 위반이다.
- 사용자 요청 근거는 얇다(앱스토어 리뷰 표본이 작다). 우리 피드백 데이터(routes/feedback.js)를 먼저 보는 것이 가장 확실하다.
