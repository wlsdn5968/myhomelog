## 5. 관리 규칙 (앞으로)
1. 용량은 §1 의 합계 쿼리로만 말한다(`db_size_mb`·`get_db_size_bytes` 는 105 에서 같은 식으로 교체).
2. 새 테이블·인덱스는 **행당 바이트 × 예상 행수**를 계획서 "전제 확인" 에 적는다. 조회 키가 반복되면 단일 키 B-tree(중복 제거) 우선 — 복합키·`INCLUDE` 는 중복 제거가 안 된다.
3. 대량 적재는 정지선 = 한도 − (월 증가 × 확보 개월) − 일시 증가분, 그리고 "되찾은 공간을 다시 채우지 않는" 하한을 둔다. 적재 후 1주 안에 재측정.
4. 통째 upsert 금지 — 바뀐 행만 쓴다(apt_master 가 힙의 절반을 빈 공간으로 들고 있는 이유).
5. 로그성 테이블은 "최신 1건 영구 + 나머지 N일" 로 보관 규칙을 명시한다.
6. 분기 1회: 부풀음 추정(§2 쿼리) 30% 초과 인덱스는 적재 창(17~19시 UTC) 밖에서 REINDEX.

### 8.4 감시 빈틈 (전부 0 MB · 값싼 것부터)
1. **용량 시계열이 어디에도 안 남는다** — `checkDbCapacity()` 는 POST/GET 쌍둥이 양쪽에 정상 배선돼 있음을 재확인했으나, 잰 값을 `cronStats` 에 넣지 않아 "지난달 대비 얼마나 늘었나" 를 물을 수단이 없다. `cron.js` 3줄 + `cronStats` 화이트리스트 1줄이면 된다.
2. **테이블별 급증이 안 보인다** — 전체 합계만 보므로 한 테이블만 폭증해도 합계가 임계 아래면 침묵한다.
3. **autovacuum 정지가 안 보인다** — `apt_geocache` 가 이미 29일째 미실행인데 어떤 신호로도 드러나지 않았다(이번 감사로 처음 발견).
4. **인덱스 부풀음 재발 감시가 없다**(`pgstattuple` 미설치) → §5 규칙 6 은 100% 수동. **오늘 값을 T0 기준선으로 고정**: `uq_molit_dedup` 59.09 B/행 · `molit_transactions_pkey` 22.51 B/행. 분기마다 재측정해 30% 초과 시 REINDEX.
5. §5 관리 규칙 6개 중 **3개만** 테스트로 강제되고 나머지 3개는 강제 수단이 없다.

### 8.5 이번 라운드가 놓쳤다가 잡힌 것 (방법 기록)
- **렌즈 5개 전원이 `molit_apt_index`(MV, 5.58 MB)를 통째로 빠뜨렸다.** "상위 테이블" 목록을 `relkind='r'` 로만 뽑아 MV(`relkind='m'`)가 빠진 탓이다. 완결성 비평이 이를 잡았고, **같은 시각 독립적으로 돌린 Plan 107 독자 재조사도 같은 객체를 최대 위험으로 지목**했다(부록 A-2). 교차 확인이 됐다. → **교훈: 크기 조사 쿼리는 `relkind in ('r','m','p')` 로 던진다.**
- **렌즈 2개가 죽은 튜플 비율을 잘못 계산했다**(분모를 `n_live_tup` 만으로 잡아 14.04%를 16.33%로, 5.07%를 5.34%로). 비평이 두 건 다 재현해 정정했다. → **교훈: `dead_pct = n_dead_tup / (n_live_tup + n_dead_tup)`.**
- **렌즈 1건이 `building_register` 증가율을 4배 과대 추정했다**(§8.3). 비평도 이건 못 잡았고 **계획자가 `fetched_at` 의 의미를 되물어 기각**했다. → **교훈: `created_at` 이 없는 테이블에서 `fetched_at` 창으로 "신규 행" 을 세면 재조회가 섞인다. 초기 일괄 적재 구간이 창에 들어 있는지 항상 확인한다.**
