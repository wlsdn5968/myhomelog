## 왜 중요한가

`frontend/index.html:3656-3667` (현재 코드 전문):

```js
      // ATTR-ACTIVATION-2026-09-06:
      // [왜] search 는 first_load 보다 훨씬 자주 일어난다. 상한 없이 보내면 admin 집계의 1000행 캡을
      //   검색 이벤트가 혼자 먹어 first_load·signup·report 가 밀려난다 — 퍼널을 보려고 만든 계측이
      //   퍼널을 못 보게 만든다. 세션당 1회면 "이 방문에서 검색까지 갔는가" 라는 퍼널 질문에 충분하다.
      sendOnce: function(event){
        try {
          var k = 'mhl_attr_1_' + event;
          if (sessionStorage.getItem(k)) return;
          sessionStorage.setItem(k, '1');
        } catch(_){ /* sessionStorage 불가(프라이빗 모드 등) — 가드 없이 1회 보낸다 */ }
        this.send(event);
      },
```

**주석은 "가드 없이 1회 보낸다" 라고 적었지만 실제 동작은 "호출할 때마다 보낸다" 다.**

감사자 실측(본문을 **한 글자도 바꾸지 않고** 옮겨 스텁 `sessionStorage` 로 5회 호출):
- 정상 `sessionStorage` → `send` **1회** (의도대로)
- `setItem` 만 throw(쿼터 초과·사파리 프라이빗 계열) → `send` **5회**
- `getItem` 부터 throw(사이트 데이터 전면 차단) → `send` **5회**

**Why:** `getItem` 과 `setItem` 이 **같은 `try` 안**에 있고, `catch` 뒤에서 `this.send(event)` 가
**조건 없이** 실행되며, 실패를 기억하는 **인메모리 플래그가 없다.**

### 왜 이 프로젝트에서 특히 문제인가

- 호출부는 `:4688`(보고서 성공)과 `:6702`(검색 성공) 두 곳이고, **검색은 한 세션에 여러 번** 일어난다.
- 이 서비스의 유입은 **카카오·인스타 인앱 브라우저**다(마케팅 자산이 인스타·스레드 기반). 그 집단이
  정확히 스토리지 제약이 흔한 환경이다.
- 위 주석이 스스로 밝힌 목적(admin 집계 1000행 캡을 검색 이벤트가 독식하는 것 방지)이
  **그 집단에서만 무력화**된다 — 퍼널을 보려고 만든 계측이 그 집단의 퍼널을 가린다.
- ⚠ 감사자도 **영향 규모(해당 브라우저 비율)는 측정하지 않았다**. 지금 사용자 수에서는 당장
  캡을 먹지는 않는다. 그래도 **주석이 사실과 다르다**는 것 자체가 다음 조사자를 오도한다.
