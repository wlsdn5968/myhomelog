# 202. 화면 한 파일 나누기 (0단계와 1단계 끝, 미배포)

작성 2026-11-16. 출처는 전면 감사 발견 18(`AUDIT_REPORT.md` 15절). 운영자 승인 "권고대로 진행"에 따라 계획만 세웠고 코드는 바꾸지 않았다. 실행은 단계마다 운영자 승인 뒤에 한다.

진행(2026-11-16, 운영자 승인 "권고대로 진행해줘. 승인할게"): 0단계와 1단계를 한 커밋으로 했다. 거래 체크리스트와 갈아타기 계산 443줄을 `frontend/js/swap-checklist.js` 로 글자 그대로 옮겼다. `npm run verify` 1,252개 통과, 로컬 미리보기에서 두 화면 확인.
계획과 달라진 점: 빈 파일로 경로만 먼저 배포하지 않았다(배포 지시가 없어 한 번에 묶였다). 그래서 배포 직후 `/js/swap-checklist.js` 가 200 과 javascript 형식으로 오는지부터 본다. 아니면 그 커밋을 되돌린다. 파일을 못 받으면 화면이 "화면 일부를 불러오지 못했어요. 새로 고침해 주세요"를 띄운다.
검사에서 배운 것: 깨진 검사는 조사대로 4개 파일이었다(`audit-1116`, `audit-full-1115`, `deal-checklist`, `swap-helper`). 화면 코드를 읽는 줄을 `backend/testSupport/readFrontend.js` 로 바꾸면 됐다. 정규식 기준선은 파일별이라 옮긴 3건을 새 파일로 다시 적어야 했다(`node scripts/check-regexp-ratchet.js --update`, 합계 73 그대로). 린트는 파일을 따로 보므로 파일 사이 전역 이름을 `eslint.config.mjs` 끝의 두 묶음에 적는다.

표기: [확인됨]은 2026-11-16 에 직접 센 것, [조사]는 낮은 등급 에이전트가 파일과 줄 번호로 보고했고 다시 세지 않은 것, [추정]은 근거가 약한 것이다.

## 왜 하는가

- `frontend/index.html` 은 약 17,000줄이고 그중 한 스크립트 덩어리가 약 12,600줄이다. [조사: 4300~16960행]
- 고칠 때마다 다른 기능에 닿을 위험이 크고, 검사 75개가 이 파일을 글자로 읽어 작은 문구 변경에도 검사가 깨진다. [조사]
- 같은 계산이 화면과 서버에 두 벌 있다(취득세율, LTV, 평 환산). 2026-11-16 에 LTV 한 건을 세 곳에서 같이 고쳐야 했다.

## 지금 구조에서 확인한 사실

- 빌드 단계가 없다. 번들러를 쓰지 않는다.
- HTML 속성으로 전역 함수를 부르는 곳이 많다. `onclick=` 만 407곳이다. [확인됨: grep 으로 셈] 모듈 방식(`type=module`)으로 바꾸면 이 호출이 모두 깨진다.
- 서비스 워커 `frontend/sw.js` 는 푸시 알림만 다루고 fetch 처리와 캐시가 없다. [확인됨: grep 0건] 그래서 옛 화면과 새 스크립트가 서비스 워커 때문에 섞일 일은 없다.
- `vercel.json` 에 `/js/` 경로가 없다. 마지막 경로 `/(.*)` 가 404 페이지를 돌려주므로 새 파일에는 전용 경로가 필요하다. [확인됨]
- 린트는 인라인 스크립트만 뽑아 본다(`scripts/extract-inline-js.js` 40행, `src=` 가 있는 태그는 제외). `npm run lint` 대상에 `frontend/` 가 없어 새 파일은 린트 밖에 놓인다. [확인됨]
- 서버 함수 묶음에는 `frontend/index.html` 만 들어간다(`vercel.json` includeFiles). [확인됨]
- CI 의 인라인 구문 검사와 `scripts/security-regression-check.js` 도 `frontend/index.html` 만 본다. 스크립트를 밖으로 빼면 이 검사들이 그 코드를 못 본다. [조사]
- 전역 상태를 여러 기능이 함께 쓴다. 대표는 `mapObj`, `CFG`, `props`, `currentDetail`, `cmpSel`, `window._popMarkers`, `window._ecosMortgageRate`, `isRegFront`. [조사] `calcLTV` 는 전역 금리와 규제 판정에 기대므로 그대로는 순수 함수가 아니다.

## 하지 않을 것

- 번들러 도입과 모듈 방식 전환. 빌드 단계가 없다는 전제, 407곳의 속성 호출, CSP, 검사 75개, 린트 추출, CI 구문 검사를 한꺼번에 다시 짜야 한다.
- 스크립트 덩어리 전체를 한 번에 나누기. 깨지는 검사가 많아 회귀 원인을 가릴 수 없다.
- 서버 함수가 화면 파일을 불러 쓰게 하기. 함수 묶음과 CPU 에 영향을 준다. 두 벌 계산은 코드 공유보다 "화면 값과 서버 값이 같은지" 대조하는 검사로 묶는다(지금 `cap-metro-1116.test.js` 가 하는 방식).

## 단계

0. 준비(화면 동작은 그대로)
   - 검사용 도우미 `readFrontend()` 를 만든다. `index.html` 과 `frontend/js/*.js` 를 이어 붙여 돌려준다. 1단계에서 건드릴 검사부터 이 도우미를 쓰게 바꾼다.
   - `vercel.json` 에 `/js/(.*)\.js` 경로를 넣는다. 캐시는 `max-age=0, must-revalidate`, `X-Content-Type-Options: nosniff`.
   - `eslint.config.mjs` 와 lint 명령에 `frontend/js` 를 넣는다(일반 스크립트, 브라우저 전역). CI 구문 검사와 보안 회귀 검사도 같은 폴더를 보게 한다.
   - 빈 파일 하나로 먼저 배포해 경로와 헤더를 운영에서 확인한다.
1. 갈아타기와 거래 체크리스트(`_swp*`, `_dcl*`, 약 510줄과 전용 스타일)를 `frontend/js/swap-checklist.js` 로 옮긴다. 다른 기능과 닿는 곳이 적다. 깨질 검사는 4개로 조사됐다. [조사]
2. DOM 을 읽지 않는 계산 함수(`_pickTierRate`, `calcLoanLimitsPure`, `computePolicyLoan`, `_swpComm` 등)를 `frontend/js/calc.js` 로 옮긴다. 깨질 검사는 12개로 조사됐다. [조사] `calcLTV` 는 금리와 규제 판정을 인자로 받게 바꾼 뒤에 옮긴다.
3. 취득세 계산(지금은 `showDetail` 안에 있음)과 평 환산 3.3058(7곳)을 함수로 먼저 뽑는다. 동작이 같은지 검사로 확인한 다음 단계에서 옮긴다.
4. 정책 타임라인 같은 자료 상수, 그다음 청약, 브리핑, 도우미 순으로 옮긴다.
5. 지도와 단지 상세는 마지막이다. `showDetail`(약 750줄)은 옮기기 전에 안에서 먼저 나눈다.

## 단계마다 지킬 것

- 옮기기만 한다. 같은 커밋에서 동작을 바꾸지 않는다.
- 스크립트는 일반 `<script src>` 로 본체보다 앞에 둔다. 전역 이름이 그대로 살아 속성 호출이 유지된다.
- 새 화면이 옛 스크립트와 섞이지 않게 캐시 헤더를 `max-age=0, must-revalidate` 로 둔다. 파일을 못 받았을 때 화면이 조용히 죽지 않도록 본체 첫머리에서 필요한 함수가 있는지 확인하고 없으면 새로 고침 안내를 띄운다. [추정: 실제 실패 빈도는 재 본 적 없음]
- `npm run verify` 통과, 로컬 미리보기(`home-preview`) 확인, 배포 뒤 운영 크롬에서 해당 기능을 눌러 본다.
- 되돌리기는 커밋 하나 되돌리기다.

## 정해야 할 것(운영자)

- 0단계와 1단계를 시작할지. 권고는 시작이다. 0단계는 화면 동작이 그대로이고 1단계는 닿는 범위가 가장 좁다.
- 배포 묶음. 0단계는 다른 코드 배포에 묶고, 1단계부터는 단계마다 한 번씩 배포해 문제가 나면 그 단계만 되돌린다. 하루 배포 3회 한도 안에서 한다.
