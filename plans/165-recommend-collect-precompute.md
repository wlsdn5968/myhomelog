## 4. 남은 설계안 A — 야간 사전 계산(구별 6개월 거래 스냅샷)

**내용**: 실거래 적재(17:00~17:30 UTC) 뒤 cron 이 구별 6개월 거래 행을 `computed_snapshots`(이미 있는 표, Plan 161) 에 저장. 추천은 구별 질의 25~47개 대신 **스냅샷 키 묶음 1회 조회**(또는 시도별 1키). 스냅샷이 없거나 오래됐으면 지금 경로로 폴백.

**측정·추정 근거**
- 전국 6개월 거래 152,433행(123개 코드), JSON 27MB. 표본 250행 실측: 행당 176B, gzip 8.3배 → **gzip 약 3.3MB**. jsonb 그대로 두면 pglz 가 gzip 보다 못해 **5~6MB 추정**. DB 439/500MB(93% 경보 465MB 까지 26MB) 에서 수용 가능하지만 매일 덮어쓰기라 dead tuple·VACUUM 고려.
- 읽기: 서울 4.6MB(비압축) 1회 전송 — 같은 리전(ap-northeast-2 ↔ icn1). 소요는 **미측정**(추정 0.3~0.8초). gzip bytea 로 저장하면 전송 0.6MB + Node 해제.
- 효과(추정): 콜드 첫 검색 수집 1.7~2.3초 → 1초 미만. 웜 인스턴스는 지금도 node-cache 6시간이라 차이 없음.

**위험·결정 사항**
1. DB 용량 +3~6MB(운영자 승인 필요 — 공유 운영 DB 쓰기 패턴 추가).
2. 신선도: 적재 직후 ~1시간은 구 스냅샷(지금은 적재 즉시 반영). 적재 cron 끝에서 바로 갱신하면 거의 없앨 수 있음.
3. 결과 동일성: 같은 행을 같은 `analyzeTransactions` 에 넣으므로 점수는 동일해야 함 — 배포 전 스냅샷 경로와 직접 경로 결과를 비교하는 테스트 필수.
4. Redis 복구(11-01 확인 예약) 뒤엔 결과 캐시 3시간이 인스턴스 간 공유돼 콜드 검색 빈도 자체가 준다 — **그때 다시 재면 A 가 필요 없을 수도 있다.**
