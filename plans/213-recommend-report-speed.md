### 2단계 후보 1 구현 (2026-11-27, 운영자 승인 "권고대로 진행해줘. 가능하면 한번에 하고, 문제가 있으면 나눠서", 미배포)

무엇: 보고서 후보 풀을, 지역 조건이 lawd_cd 목록 25개 이하일 때 구별 거래 기억(`getRegionRecentTransactions(구, 6)`)을 걸러서 만든다. 서울 광역(25구)과 인천 광역(14구), 구 단위 선택이 해당하고, 경기 광역(47구)과 이름 like 분기, 전국은 종전 조회 그대로다. 구별 기억에 `id`, `deal_date` 두 열을 더했다(추천 경로는 이 둘을 읽지 않고 응답에도 싣지 않는다. 응답 필드는 고른 것만 쓴다, `analyzeTransactions` 의 `recentTx`).

같은 결과의 근거:
- 지역 판정 분기는 바꾸지 않았다. 그 결과인 적용 함수에서 lawd_cd 목록만 읽는다(`_lawdCodesOfRegionOp`, in 하나일 때만).
- 거르기(면적, 가격 양끝 포함, 시작일), 순서(deal_date desc, id desc), 상한(12,000), complete 판정(상한보다 적을 때만 true)이 종전 조회와 같다(`_poolFromRegionRows`).
- 같다고 장담할 수 없으면 종전 조회로 간다: 구 하나라도 못 받음, 구 하나가 12,000행 이상, 빈 값이 든 행(기억이 빈 값을 '' 나 0 으로 담아 구별할 수 없다), id 나 deal_date 없음.
- 운영 DB 조회(2026-11-27): 6개월 창 150,544행에 빈 값과 빈 문자열 0. 서울 창 23,369행에서 deal_date 와 년월일 불일치 0. Postgres JSON 변환은 면적, 금액, id 를 숫자로 준다(id 약 1,280만).
- 검사 `backend/test/report-pool-region-1127.test.js`(6개): 실제 매핑 코드(`getRegionRecentTransactions`)를 가짜 DB 로 거친 결과와, 원본에 SQL 과 같은 조건과 순서를 적용한 기대값을 세 가지 자료와 세 가지 조건으로 견준다(구를 넘나드는 날짜 동점 포함). 자료 날짜는 실행하는 날 기준이라 날이 지나도 비지 않는다. 코드를 일부러 다섯 군데 망가뜨려(id 순서, 시작일 조건, 가격 경계, 면적 경계, 구 12,000행 검사) 모두 잡는 것을 돌려 봤다.

종전과 다른 점(알고 받아들인 것):
- 기억이 최대 6시간 묵을 수 있다. 보고서 응답 기억도 6시간이라 같은 범위다.

- 콜드 인스턴스에서는 25구 전체 거래(서울 23,369행)를 읽어 종전 풀(가격대 안 최대 12,000행)보다 읽는 행이 많다. 같은 인스턴스에서 단지 찾기가 먼저 돌았으면 DB 를 읽지 않는다. 배포 뒤 `report-stages` 의 pool 과 poolViaRegion 칸으로 시간을 다시 잰다.

반증 검토(낮은 등급 에이전트, 2026-11-27): 종전 조회와 결과가 달라지는 입력은 찾지 못했다. 받은 지적과 처리:

판단:
- 단독으로는 1초가 안 걸리는 조회가 11-27 단지 찾기에서 각 약 4초였다. 같은 순간에 25구 거래 조회(구마다 최대 4쪽 병렬)와 함께 나갔으므로 대기의 큰 몫은 DB 경합으로 본다(몫의 크기는 확인 불가).
- Redis 로 옮기면 서버가 새로 뜰 때마다 약 1MB 를 내려받는다. 월 전송량 10GB 를 함께 쓰고, 이 Redis 는 2026-10 에 월 명령 한도를 넘겨 쓰기가 멈춘 이력이 있다(`docs/ops/redis.md`). 지금의 월 사용량은 Upstash 콘솔에서만 보여 확인 불가.
- 그래서 지금은 하지 않는다. 후보 1(보고서 풀 기억 공유) 배포 뒤 report-stages 와 단지 찾기 단계 로그를 다시 재서 경합이 줄었는지 본 다음 정한다. 그때도 크면 Redis 보다 먼저, 비용이 들지 않는 쪽(별칭 대응표의 쪽을 차례 대신 병렬로, 또는 두 조회를 25구 거래 조회보다 조금 먼저 시작)을 측정과 함께 검토한다.

배포 뒤 확인: 보고서 한 번을 `report-stages` 로 재서 11-27 실측(pool 10,805ms, 전체 23,703ms)과 견주고 poolViaRegion 칸이 있는지 본다. 같은 조건의 응답은 Redis 에 6시간(21600초) 기억돼 배포 직후 같은 조건이면 옛 답이 나온다. 그래서 6시간 뒤에 재거나 조건 하나를 바꿔 잰다. 11-27 회차의 후보 목록은 저장하지 않아 배포 전후 후보 비교는 확인 불가이고, 같은 결과의 근거는 위 검사다.

## 하지 않은 가정

- 어느 조회가 시간을 쓰는지는 모른다. 그래서 고칠 곳을 정하지 않았다.
- 응답 기억(캐시)으로 줄어들지도 모른다. 조건 조합이 많아 적중률이 낮을 것 같지만 측정하지 않았다.

## 순서

1. 측정(읽기 전용, 운영 부하 없이): 로컬에서 두 경로를 가짜 DB 로 돌려 조회 횟수와 순서를 센다. 운영은 운영자가 화면을 쓸 때의 cpu-meter 로그(1시간 안)와 `pg_stat_statements` 의 해당 조회 평균으로 본다. 조회마다 걸린 시간을 표로 남긴다.
2. 표를 보고 계획을 고친다. 후보: 하루 한 번 바뀌는 재료(지역별 후보 단지, 점수 재료)를 예약 작업 스냅샷으로 미리 만들고 요청 때는 거르고 정렬만 하는 형태, 같은 조회의 중복 제거, 병렬로 묶을 수 있는 순차 조회.
3. 고친 뒤 같은 조건으로 다시 재서 전후를 남긴다. 점수와 순위가 바뀌면 안 된다(같은 입력의 상위 15곳 비교 검사).

## 위험과 선행 조건

- 점수와 순위가 바뀌면 사용자에게 다른 결과가 보인다. 바꾸기 전후 결과를 견주는 검사가 먼저다.
- 새 예약 작업은 CPU 를 먼저 잰다(저장소 금지 사항: 팀 Active CPU 30일 합계 한도).
- 운영자 승인 뒤 실행한다.
