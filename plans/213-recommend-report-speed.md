읽은 것:

- 보고서 22.7초 중 CPU 1.5초를 빼면 약 21초가 대기다. DB 평균만으로는 이를 다 설명하지 못하므로 외부 호출(카카오 주변 시설 묶음 순차, 건축물대장 사슬, 전월세 API 페이서)이 후보다. 어느 것이 얼마인지는 단계별 시간 기록이 없어 확인 불가.
- 최대값(7초대)은 여러 조회에서 비슷하게 나온다. 같은 시각에 다른 무거운 작업과 겹쳤을 가능성이 있으나 확인 불가.

다음 측정(코드 한 곳, 동작 그대로, 운영자 승인 뒤): 두 경로의 단계마다 걸린 시간(wall ms)과 외부 호출 수를 기존 cpu-meter 로그 한 줄에 붙인다. 운영자가 같은 조건으로 한 번씩 눌러 1시간 안에 로그를 읽는다. 그 표를 보고 2단계(계획 고치기)로 간다.

## 하지 않은 가정

- 어느 조회가 시간을 쓰는지는 모른다. 그래서 고칠 곳을 정하지 않았다.
- 응답 기억(캐시)으로 줄어들지도 모른다. 조건 조합이 많아 적중률이 낮을 것 같지만 측정하지 않았다.

## 순서

1. 측정(읽기 전용, 운영 부하 없이): 로컬에서 두 경로를 가짜 DB 로 돌려 조회 횟수와 순서를 센다. 운영은 운영자가 화면을 쓸 때의 cpu-meter 로그(1시간 안)와 `pg_stat_statements` 의 해당 조회 평균으로 본다. 조회마다 걸린 시간을 표로 남긴다.
2. 표를 보고 계획을 고친다. 후보: 하루 한 번 바뀌는 재료(지역별 후보 단지, 점수 재료)를 예약 작업 스냅샷으로 미리 만들고 요청 때는 거르고 정렬만 하는 형태, 같은 조회의 중복 제거, 병렬로 묶을 수 있는 순차 조회.
3. 고친 뒤 같은 조건으로 다시 재서 전후를 남긴다. 점수와 순위가 바뀌면 안 된다(같은 입력의 상위 15곳 비교 검사).

## 위험과 선행 조건

- 점수와 순위가 바뀌면 사용자에게 다른 결과가 보인다. 바꾸기 전후 결과를 견주는 검사가 먼저다.
- 새 예약 작업은 CPU 를 먼저 잰다(저장소 금지 사항: 팀 Active CPU 30일 합계 한도).
- 운영자 승인 뒤 실행한다.
